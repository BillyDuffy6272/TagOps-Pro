## Whose decision RLS-first was

Worth being explicit about, since it's a fair walk-through question: **RLS as the primary authorisation mechanism was my own architectural decision, made in Week 2 — `decision-log.md` ADR-0003 (13/05/2026) — before any feature code existed**, in direct response to the AT3 brief's security-floor requirement #2. It's also codified as a standing instruction in this project's own `CLAUDE.md` ("Default to RLS-first thinking — design the policy before the query"), which every Claude Code session is required to follow, not something any individual session proposed on its own initiative. What Claude Code did within that already-decided architecture was implement and, later, audit specific policies against it — proposing SQL, which I reviewed, accepted, modified, or in a few cases (see `decision-log.md` ADR-0029's accessibility rollback) explicitly rejected. The choice of RLS itself predates that work; the policy text implementing it doesn't need to be reinvented as "my idea" to still be my decision.

## Threat model

The realistic attackers here aren't anonymous strangers so much as people who already have *some* legitimate access and are testing what else they can reach:

- **(a) No account at all.** Blocked by Supabase Auth at the front door — every table's RLS policies require `auth.uid()` to resolve to a real, signed-in user; there is no anonymous read path (`enable_anonymous_sign_ins = false`).
- **(b) A signed-in user trying to reach another organisation's data.** This is the one that actually broke, twice. A self-referential `WHERE organisation_id = organisation_id` clause inside an RLS policy's subquery — where an unaliased `FROM public.organisation_members` in the subquery shadows the outer row being inserted — collapses the check to "does this user hold *any* role in *any* org," not "in the org they're inserting into." It was fixed for `tags`/`triggers`/`variables`/`conversion_events` in June (`20260610000000_fix_domain_insert_rls.sql`) and, when a full audit re-traced the same pattern in August, found still present on `containers` and — more seriously — on `organisation_members`'s own INSERT policy, where it would have let an admin of one org insert a membership row (any role, including `owner`) into a completely unrelated org. Both were fixed in `20260827000000_fix_remaining_rls_gaps.sql`. The lesson this actually teaches: the same category of RLS mistake can hide in more than one policy, and finding it once doesn't mean every instance is gone — it's worth a deliberate pass over every `WITH CHECK` clause, not just the ones that already misbehaved.
- **(c) A legitimate team member with a lower role trying to act like a higher one.** The clearest example: `ASSIGNABLE_ROLES` in the UI deliberately excludes `owner` from the role-editing dropdown, but that alone doesn't stop a request crafted outside the UI. The `organisation_members` UPDATE policy now carries a `WITH CHECK (role <> 'owner' AND ...)` so the database itself refuses to let any UPDATE result in a new owner, regardless of what the client sends.

## RLS reasoning

Two patterns recur across the policies and are worth calling out explicitly rather than leaving as "RLS is on":

**`is_active_org_member(org_id)` is `SECURITY DEFINER` on purpose.** A membership-select policy that queries the `organisation_members` table to decide whether the caller can *see* `organisation_members` rows is circular under normal RLS — the policy would need to evaluate itself. Making the helper function `SECURITY DEFINER` with `set search_path = ''` (and fully-qualifying every table reference inside it) breaks that circularity safely: it runs with the function owner's privileges, but only ever answers one narrow, hardcoded question (is `auth.uid()` an active member of this org?), so it can't be turned into a general privilege-escalation tool the way a careless `SECURITY DEFINER` function could be.

**Column-level privilege revocation as belt-and-suspenders beyond RLS.** `organisations.invite_code` has `SELECT`/`UPDATE` revoked from `authenticated`/`anon` entirely — even a correctly-written RLS policy allowing "members can select organisations" would otherwise let any viewer read the invite code and hand it out. Access goes only through three narrow `SECURITY DEFINER` functions (`get_invite_code`, `regenerate_invite_code`, `redeem_invite_code`), each independently re-checking the caller's role. This is a second, independent layer, not a substitute for RLS — it means a mistake in the table's general RLS policy still wouldn't leak this specific column.

## Secrets and key management

Supabase issues two keys: the **anon key**, safe to ship in the browser bundle because every table it can touch is behind RLS, and the **service-role key**, which bypasses RLS entirely and must never leave a trusted server. TagOps-Pro has no trusted server, so the service-role key is never used anywhere in this codebase — confirmed by grep, not just asserted. `.env.local` (holding the anon key and project URL for local dev) and `.env` generally are excluded via `.gitignore`; the same two values are set directly in Vercel's project settings for production, never committed.

## Known limitations / residual risk

Being explicit about what's *not* solved is more useful than implying everything is:

- **No Content-Security-Policy.** Not part of the six-item floor, but cheap, meaningful defense-in-depth this app doesn't have yet — no `<meta http-equiv="Content-Security-Policy">` in `index.html`, no equivalent header set via Vercel.
- **`redeem_invite_code()` has no explicit rate limit.** The 8-character base36 code has enough entropy (~2.8×10¹²) that brute-forcing is impractical at any rate PostgREST's general limits would allow, but there's no dedicated throttle on repeated guesses.
- **Password minimum is Supabase's default (6 characters, no complexity rule).** Currently moot — there is no password sign-in path — but this would need raising before an email/password option is ever added.
- **The Google OAuth `provider_token` sits in `localStorage`** via supabase-js's default session persistence. No live XSS vector was found in this codebase (no `dangerouslySetInnerHTML`, `eval`, or unescaped interpolation into rendered HTML anywhere in `src/`), so this isn't exploitable today — but it means a future XSS bug would hand an attacker a live, scoped Google API token, not just app data.

## Worked example: a real injection bug, found and fixed

> **Note (28/08/2026):** The conversion-event feature this example is about was removed from the product on the same day (ADR-0038, `decision-log.md`) — `src/features/conversions/` no longer exists. Kept here rather than deleted because it's real, verifiable evidence of the security-floor process actually catching and fixing an injection-class bug, and the defense-in-depth pattern it demonstrates (client regex + database `CHECK` + escaped code generation) is the same pattern applied everywhere else in the app.

`src/features/conversions/lib/snippets.ts` generated copy-paste JavaScript meant to be pasted directly onto a customer's live website (a `gtag()` call or a `dataLayer.push()`). Two fields — `value_param` and `display_name` — were originally interpolated into that generated code as raw template-literal substitutions, with no database `CHECK` constraint and no client-side format rule (unlike `event_name`, which already had both). A crafted `value_param` containing a stray quote could break out of its intended position as a JS object key; a `display_name` containing a newline could break out of a `//` comment line into executable code — in both cases, arbitrary JavaScript would run on the business owner's real production site once the snippet was pasted in. The fix (27/08/2026) was defense-in-depth at every layer this review argues for: the generator escaped every interpolated value as a proper, quoted JS string literal and stripped line breaks from anything placed inside a comment; matching `CHECK` constraints were added at the database; matching validation was added to the form; and two adversarial tests (a quote-injection attempt, a newline-injection attempt) were added specifically because the existing tests were happy-path only, which is how the gap went unnoticed in the first place.
